# Load review, slice 1 (OCR providers)

Measured on this Windows box: tesseract present, no network.

## Measured
- load_settings: 1.3 ms/call (toml parse + secret scan). Negligible vs OCR; per-page call is fine. Stale-config risk if cached, so leave uncached or cache per document.
- PNG encode of 2200x1700 RGB page (11.2 MB raw): 67 ms/page (cloud and tesseract both pay it).
- Tesseract blank page via stdin subprocess: 0.27 s/page (mostly process startup); 60 pages ~16 s+ real text more. Sequential.
- 8 threads x 0.2 s fake work under pdf_front._DOCUMENT_LOCK: 1.60 s (fully serialised).

## Ranked issues
1. HIGH, global serialisation + remote OCR starvation. pdf_front.py:122 `_DOCUMENT_LOCK` wraps the whole read_words, including cloud OCR. One document of 60 pages on a cloud engine (each page up to 3 backoffs 7 s + poll up to 120 s + 60 s HTTP timeout) can hold the lock for tens of minutes; every other request (even text-layer PDFs, roles endpoint inference.py:196) blocks behind it. Admission (admission.py:17) allows 2 inflight but both end up at this lock, so effective concurrency is 1; queue_timeout is 30 s so followers get queue_timeout/503 only while waiting for slots, but once admitted they sit on the lock with no timeout. Fix: lock only for non-thread-safe pdfium use per document open, or drop it for the OCR calls; add a per-document wall-clock deadline (e.g. 300 s) checked between pages in _read_words and raise EngineFault.
2. HIGH, no per-provider concurrency or cost cap. ocr_cloud._send has no semaphore; today the lock hides it, but removing the lock (fix 1) exposes vendors to N parallel pages. Add module-level `threading.BoundedSemaphore(n)` per engine id (default 2-4, option `max_concurrency` in the toml) acquired in `_CloudEngine.read_page` (ocr_cloud.py:191), plus a process-wide page budget counter (env OPENBOOKS_CLOUD_PAGES_PER_HOUR, reject with CapabilityRefused when exceeded). Admission max_pages=60 (admission.py:20) is estimated pages, not remote-only; cap remote pages separately in the same place (admit, app.py `_count_ocr_pages`).
3. MEDIUM, retry/backoff. ocr_cloud.py:29,93-100: fixed 1/2/4 s, no jitter, ignores Retry-After header, sleeps while holding the lock; retries only 429 for POST (good: avoids double billing), all 5xx for GET. Fix: delay = max(Retry-After, backoff) * uniform(0.5,1.5); cap total retry sleep per page. Worst-case per page today: 3 x 60 s HTTP + 7 s backoff ~ 3 min on POST, Azure poll adds up to 120 s. Per-document 60 pages worst case is hours; hence deadline in 1.
4. MEDIUM, last_ocr_run staleness. pdf_front.py:67 sets thread-local `_RUNS.run` per page (last page wins, overwritten each page, never cleared). Reproduced: a stale value on a thread persists into the next document, and a text-layer-only document on a reused to_thread worker thread returns the previous document's run. Only caller is harness/bench/ocr_compare.py:142. Fix: clear `_RUNS.run = None` at start of _read_words (and merge per-page runs or return run from read_words). Under asyncio.to_thread the default pool reuses threads, so staleness is real.
5. MEDIUM, per-page ocr_pages call re-runs select_engine/_build_engine each page (pdf_front.py:62-66; each page builds a new engine, two select_engine calls per page, plus fallback built per page). Cheap for tesseract; for cloud it re-creates engine/transport and means the fallback decision is per page, so one document can mix engines and `OcrRun.fallback` is per page. Fix: select engine once per document in _read_words and pass pages as a batch or reuse the engine.
6. MEDIUM, tesseract timeout. subprocess.run(timeout=60) kills the child on TimeoutExpired (Python does kill+wait on POSIX and Windows), so no zombie; but tesseract spawns its own OpenMP threads: set env OMP_THREAD_LIMIT=1 when running pages in parallel, otherwise N parallel tesseracts oversubscribe CPUs. Timeout maps to ProviderUnavailable which triggers fallback for the whole document including already-read pages (re-reads everything, ocr_providers.py:401-407).
7. LOW, memory: page at 200 DPI max 3200 px: ~3200x2500x3 = 24 MB raw per page plus PNG copy (~1-5 MB) plus base64 (+33%) for cloud (300 DPI, capped at 3200 px, same bound). Pages are rendered one at a time, so ~60 MB peak per document; fine. ocr_pages(list(pages_iter)) holds all pages only when a caller batches; pdf_front passes one.
8. LOW, EasyOCR: reader cached per use_gpu under lock (ocr_providers.py:285-302), good. First load is slow and blocks callers holding the lock; readtext on one shared Reader from several threads is not documented as thread-safe, and on GPU concurrent calls contend for VRAM. Keep EasyOCR behind its own `threading.Lock` around readtext if _DOCUMENT_LOCK is relaxed.
9. LOW, registry: `_REGISTRY` writes are locked (register_engine) but `_lookup_factory` reads/checks `engine_name not in _REGISTRY` without lock; register_all is idempotent so the race only causes duplicate registration. Safe.

## Server behaviour with N concurrent uploads
admission.py: max 2 running + 8 queued, 256 MB bytes, 60 OCR pages; 10th request gets queue_full with Retry-After 5; waiters poll every 20 ms and drop after 30 s or on disconnect. Good backpressure at the door, but the _DOCUMENT_LOCK makes the 2 running slots behave as 1, and nothing bounds time after admission. One slow remote OCR job starves all other admitted jobs (issue 1).

## Recommended order
1) per-document deadline + shrink lock scope, 2) per-provider semaphore + remote page budget in ocr_cloud.read_page, 3) Retry-After + jitter, 4) clear _RUNS at start, 5) engine once per document.
