# Free launch decision and runbook

Open Books is ready to ship as a free, local verification kit for supported documents. On the same three synthetic screenshot variants, the same Qwen model answered the closing-balance question correctly with 71–73% fewer tokens using Open Books context than using LiteParse output. The 2 GiB Docker smoke verified 18 of 18 screenshot uploads at 1.60 images per second. The longer scan run and hosted LlamaParse comparison remain release gates for broader OCR performance claims.

Research checked 2026-11-25. This document supersedes monetization suggestions in the earlier harness research. Launch OpenBooks and its skills free. Optional third-party models or services may charge the user separately; disclose provider, data transfer, and expected charges before use. Do not describe optional cloud processing as local.

## Position and proof

Present OpenBooks as a financial-document workflow focused on evidence and reconciliation, with explicit refusals when a result cannot be verified. Describe only behavior verified for the release. Do not claim best accuracy, speed, token efficiency, or superiority over LlamaParse or Mistral without a reproducible comparison.

LlamaParse documents support for merged and multi-page tables, and LlamaExtract documents field citations. Mistral OCR documents structured tables, layout blocks, confidence, and schema-based annotations. The 2026 FinNLP paper on bank statements reports 99.52% transaction accuracy over 23 statements with 1,672 transactions using a pipeline that includes LlamaParse and reconciliation. A defensible test for Open Books needs its own held-out corpus, adjudicated truth, and equivalent output requirements. [LlamaParse tables](https://developers.llamaindex.ai/llamaparse/parse/features/tables/) · [LlamaExtract citations](https://developers.llamaindex.ai/llamaparse/extract/guides/response-format/) · [Mistral OCR](https://docs.mistral.ai/studio/document-processing/basic_ocr) · [FinNLP study](https://aclanthology.org/2026.finnlp-1.13/)

Prioritize a useful outlier workflow: preserve file hash, page and source evidence for each extracted amount; reconcile opening balance plus transactions against closing balance; surface mismatches, missing pages, ambiguous signs and low-confidence rows as actionable exceptions; withhold unsupported figures rather than silently invent them. Measure exception recall and false refusals as well as extraction accuracy. These are product goals until individually verified. The current parser change reduces repeated line summation on dense PDF words; its in-process synthetic 8,000-word measurement was 0.024 s versus 12.560 s before, with pathological boundary cases still potentially quadratic. This is a microbenchmark, not an end-to-end or competitor speed claim.

## Comparison protocol

Before publishing rankings, lock a representative, legally shareable corpus and held-out cases: native and scanned statements, multi-page and borderless tables, varied currencies, missing pages, duplicate rows, negative amounts and known reconciliation failures. Publish ground truth, splits, versions, configurations, exact prompts, output schemas, scorer, raw outputs, failures, hardware, runs, and uncertainty. Use the same inputs and tasks, equivalent allowed resources and output requirements; identify unavailable features and exclusions. Report per-document and per-category results, not just a pooled score.

Score field and transaction precision/recall, exact values and signs, table structure, evidence citation correctness, reconciliation correctness, exception recall, false refusals and successful verified-answer rate. Report end-to-end latency distributions, failure rate, total cost including provider fees, and pages processed. Distinguish parser-only from agent end-to-end measurements.

For agent token efficiency, hold the model, task, answer schema, instructions and scoring fixed; record full tool schemas, messages, tool responses, retries and transcript. Separately report input, output, cached input and cache-write tokens, using the provider's definitions; run cold and warm caches separately. Count all attempts, including failures. Report total tokens divided by independently verified correct answers, alongside the numerator, number of tasks and success rate; if there are zero verified answers, the ratio is undefined. Report token usage for all tasks as well as per-success ratios so an approach cannot appear efficient by refusing hard cases. No measured rankings are available in this document.

## Measured launch baseline

The local MCP token harness ran three bundled fixtures against the built server with `cl100k_base`. All three detail levels preserved the expected two releases and one typed refusal.

| Input and detail | Request tokens | Response tokens | Total |
|---|---:|---:|---:|
| Base64 upload, standard | 1,319 | 332 | 1,651 |
| Base64 upload, verdict | 1,334 | 77 | 1,411 |
| Base64 upload, figures | 1,331 | 191 | 1,522 |
| Root-scoped file, standard | 105 | 332 | 437 |
| Root-scoped file, verdict | 120 | 77 | 197 |
| Root-scoped file, figures | 117 | 191 | 308 |

Local file references cut standard request tokens by 92% and total request-plus-response tokens by 74%. Verdict responses cut response tokens by 77% and omit figures. `tools/list` was 514 tokens and `resources/list` was 122. These are serialized payload counts. A model run is needed to measure provider billing, answer correctness, and caching.

Reproduce from the repository root with `python -m harness.bench.token_cost` after putting `harness/` on `PYTHONPATH`. Pass `--mcp-command "node packages/js/cli/dist/mcp/cli.js"` to use the local build. Run both `--input-mode upload` and `--input-mode file` with separate `--out` directories.

The paired local model experiment used Qwen2.5 0.5B Instruct Q4_K_M, LiteParse 2.21.1 with Tesseract, the same answer grammar, and a fresh context for each call. With `--task closing`, all three pipelines answered three complete visual variants of one synthetic ledger exactly. Open Books used 165 model tokens, compared with 577 for LiteParse Markdown and 619 for LiteParse text. That is 71.4% and 73.3% fewer tokens per correct answer, respectively. The broader summary experiment measured three correct answers out of five for Open Books and zero for both LiteParse arms under its final prompt. Its comparative tokens-per-correct-answer measure is undefined. The reports preserve earlier prompt trials. Generalizing this result requires varied ledgers and a held-out corpus. Hosted LlamaParse Agentic is an opt-in arm that requires a LlamaCloud key and a pinned version. [LiteParse and hosted LlamaParse](https://developers.llamaindex.ai/home/)

The seed-7 Tesseract run covered four scanned statements and 24 pages. All four refused with `PARSE_ERROR`. Median document latency was 45.33 s, p95 was 56.85 s, and there were zero wrong releases. In the separate 20-statement scan benchmark, both Tesseract and EasyOCR released 0 of 20 documents and recorded zero wrong releases. An eight-page stage benchmark measured 0.239 pages/s with one worker and 0.752 pages/s with four workers on the Windows test host. In a separate four-page comparison, faster lossless PNG encoding cut median encode time from 951 ms to 290 ms and produced identical Tesseract TSV. Mean encoded size increased from 6.4 MiB to 10.4 MiB. Use native documents and supported screenshot layouts in launch demos. [Twenty statement evidence](../evidence/ocr_compare_20_scans_2026-11-25.json)

`python -m harness.bench.screenshot_bench` verifies generated PNG fixtures with known transaction rows. It got all 15 expected decisions right across five variants repeated three times, with 180 of 180 fields exact on released cases. Cropped and tampered screenshots refused. On the Windows test host the default pipeline took 0.84 s p50 and 1.87 s p95 at 1.04 images/s serial throughput. The optional typed-role cross-check had the same decisions and field matches at 0.92 s p50, 6.93 s p95, and 0.79 images/s, including initial model loading. These fixtures cover one synthetic layout. The example bank-statement image from LlamaIndex’s publication refused `UNKNOWN_LAYOUT` in Open Books. The article reports an abbreviated parse of its source PDF, so the image run only measures Open Books coverage of that representation. [LlamaIndex’s published example](https://www.llamaindex.ai/blog/how-to-extract-tables-from-pdf)

The 2 GiB Docker run used two CPUs and passed native-PDF fixture and latency gates at 1 and 2 offered requests per second. Single-page p95 was 92 ms at 1 RPS and 205 ms at 2 RPS. The process reported 513 MiB peak RSS, zero errors and rejections, and no OOM kill or restart. With four concurrent screenshot clients, the same container verified 18 of 18 uploads at 1.60 images/s and 4.41 s p95. This was an 11.27-second run on three repeated synthetic screenshot variants. The packaged UI also passed a clean Chrome smoke test for release, tampered refusal, and a cropped screenshot with a trusted opening balance supplied.

## Distribution and release gates

1. Verify the tagged release on a clean machine using synthetic documents: install, `openbooks doctor`, a successful parse, an intentional refusal, MCP startup and each documented tool. Document Node/Python and OCR download requirements and data handling. The [npm quickstart](../../web/content/docs/npm-cli-quickstart.mdx) currently specifies Node 20+, Python 3.11+, and a potentially large engine install.
2. npm registry metadata checked 2026-11-25: `@lumeo_hq/openbooks` 0.2.4 exposes `openbooks` and `openbooks-mcp`; `@lumeo_hq/openbooks-mcp` 0.2.3 exposes `openbooks-mcp`. Both latest versions returned no deprecation field. Five other packages were already deprecated per release inventory; leave them deprecated and do not revive them. Confirm exact versions and installation on release day. Publish one clear preferred install path and explain the separate MCP package to avoid ambiguity; package metadata alone does not prove a working install.
3. Package versioned `SKILL.md` instructions and local MCP configuration in a public plugin repository. Test installation and a complete workflow in supported clients. Claude Code also discovers project skills under `.claude/skills/`; Claude's API and managed agents have distinct upload and attachment flows. See [Agent Skills](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview) and [plugin marketplaces](https://code.claude.com/docs/en/plugin-marketplaces). Document supported surfaces: a local plugin server does not run everywhere.
4. For a public Anthropic listing, submit the plugin bundle through the [developer portal](https://claude.ai/directory/manage) from the organization that should own it. A paid Claude plan and appropriate organization role are required for submission; this is an external account requirement, not a charge for OpenBooks. The repository must be public before publication, and Anthropic reviews the listing. Skills cannot be submitted alone. See [directory publishing](https://claude.com/docs/directory/publish).
5. A direct connector listing requires a remote HTTPS MCP server. A local server cannot be listed as a standalone connector; include it in the plugin. Remote submission requires applicable OAuth for user accounts, tool titles and read-only or destructive annotations, testing in Claude, documentation, privacy policy, support contact and icon. Review the [connector checklist](https://claude.com/docs/connectors/building/submission) and directory terms before submission. Do not add hosting solely to obtain a listing without a data-handling design and operational owner. Anthropic's older desktop-extension help page conflicts with the current submission guide; verify the portal requirements at submission time.
6. Publish a reproducible demo, limitations, support route and benchmark results only when ready. Track installs, successful first runs, refusals and reported defects with privacy-preserving measurement. Record directory submission and review status; no listing or approval is implied by this plan.
